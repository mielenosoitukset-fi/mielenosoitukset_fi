# Isolated Hallinto OIDC issuer

This development slice registers an issuer only when the Flask app is in test mode and its factory receives explicit `HALLINTO_OIDC` overrides. It uses the existing sign-in and sign-out routes, one registered confidential client, exact HTTPS redirect, S256 and short-lived, single-use authorization codes. The ID token carries an opaque owner login reference. The confidential `/hallinto-oidc/session` check validates the reference against the live account, epoch, credentials and per-browser revocation.

Hallinto links group memberships to accounts through `/hallinto-oidc/accounts/search` (a username or display-name prefix of 3–64 characters, at most 10 results) and `/hallinto-oidc/accounts/lookup` (at most 100 account IDs). Each call needs the confidential client and the acting account's live `sub` and `sid` reference. The account must be an `admin` or `global_admin`. Results contain only the account ID, username, display name and whether the account is active, confirmed, not banned and not suspended.

When the person has no account, `/hallinto-oidc/accounts/invite` (`email`, `username`, optional `name`) creates an ordinary `user` account for them, with an unknown random password, unconfirmed. The acting account must also hold `CREATE_USER` or full permissions. Flask emails a one-hour set-password link; setting the password through it confirms the address. The account history records `user_created` with the Hallinto admin as the actor (`via: hallinto`). An address that already has an account returns 409 with that account, so Hallinto can pick it instead. Roles are never set here.

Organization account requests (`organization_requests`, stored by the Go form; see `docs/organization-requests.md`) reach Hallinto through two calls with the same client and admin sign-in check. `/hallinto-oidc/organization-requests/list` returns at most 100 requests whose applicant has confirmed the address, newest first, with the organization's details (including the city's display name and whether a logo was uploaded, never the logo's bytes) and the applicant's name, address and optional account; requests still `unconfirmed` and the status token hash never leave Flask. `/hallinto-oidc/organization-requests/update` (`id`, `status`, optional `message`, `case`, and for a request made on the organization's behalf `access` and `invite_email`) records a handling step: the status the applicant sees, the Hallinto case and a changed access choice. Each step is appended to the request's `history` with the acting account. `/hallinto-oidc/organization-requests/create-organization` (`id`, `case`) is the owner operation of slice O4. It needs a signed-in admin with `CREATE_ORGANIZATION` and a request that is `approved` by the named Hallinto case. It creates the organization (verified, with the logo copied to the image store) and gives the owner access as the access choice says: a new account of kind `organization` on the organization's public address with a password link, the applicant's own account as owner, or an owner invitation marked `role_granted_by: hallinto:<case>`. It is idempotent: the request row remembers `organization_id`, `owner_state` and `logo_state`, and a repeat finishes missing steps. An address that already has an account gives `email_in_use`, so Hallinto can change the access choice. The update call alone creates nothing and grants no access.

`/hallinto-oidc/organization-requests/create` (same admin sign-in check) stores a request a Hallinto member typed in from Lomakkeet (phone, mail or a meeting): organization name, links, optional address, city, Y-tunnus and description, the applicant's name, optional address and role, whether the applicant represents the organization and, if so, `organization_account` or `invite` access (an own account needs a signed-in applicant). It is an ordinary `received` request with `source: hallinto-manual` and `entered_by`; it has no status link for the applicant, and it is handled in the same Hallinto case process.

City admin applications (`city_admin_applications`, stored by the Go form at `/kaupunkiadmin`) reach Hallinto the same way. `/hallinto-oidc/city-admin-applications/list` returns at most 100 applications that are open or decided (not withdrawn), newest first, with the applicant's account id, username and display name, the cities and the answers; never an email address. `/hallinto-oidc/city-admin-applications/update` (`id`, `status` = `in_review` | `approved` | `declined`, `case`) records a handling step. The first step links the Hallinto case, and later steps must name the same case. A decided application keeps its decision. Each step is appended to the application's `history` with the acting account and closes a Flask admin case made before the switch. Nothing here grants a role: the grant is the appointment Hallinto sends to the city grant writer. With `CITY_ADMIN_APPLICATIONS_IN_HALLINTO=true` the delivery job makes no admin case, so Hallinto is the only place an application is handled.

Run `python -m pytest -q tests/test_hallinto_issuer.py tests/test_hallinto_sessions.py tests/test_logout_post.py` with the development dependencies and the existing disposable test database. Coverage includes real Flask sign-in and sign-out, separate browsers, concurrent token exchange, invalid redirects and PKCE, account invalidation and disabled-by-default routes.

Production preparation still needs reviewed non-test configuration, a production dependency install, restricted key and client-secret provisioning, expiration indexes, proxy configuration and the live approval gate. The production Flask account data stays on lc-db. Hallinto receives only the authenticated identity and eligibility response and uses separate persistence for its records. Existing permission execution remains with its current owner.
