# Site 503s, November 2026

Read-only investigation, 17.11.2026 (Helsinki time; the servers log UTC, Helsinki is UTC+2 in November). Nothing on production was changed.

## What happened

The public site showed "Palvelu on tilapäisesti suljettu" at 09:31 and 09:34–09:43 on 17.11.2026. That page is the public lockdown gate answering 503. No lockdown was set. The gate (Go API, React host, Flask) read the lockdown document from MongoDB on lc-db. The read timed out, and after 30 seconds without a successful answer the gate failed closed. So a slow database closed the whole site. Fixed in the same pull request: a failed read now keeps the last answer for 15 minutes and a process without an answer stays open (see the decisions log, "Lockdown gate when the status read fails").

## Why lc-db was slow

lc-db is a KVM guest (QEMU Q35, Ubuntu kernel 6.8.0-138, 3 vCPUs, one virtio-net queue, ZFS module loaded). Findings:

- **One CPU is saturated by softirq work out of proportion to traffic.** At 09:30–09:40 `sar` shows CPU 1 at 96.8 % system time (idle 2.3 %) while the NIC moved only about 415 packets/s in and 763 packets/s (2.1 MB/s) out. The same CPU 1 hits 50–90 % system time several times a day: 11.11. 22:10–22:30, 12.11. 11:40 and 15:40, 13.11. 04:40 and 21:50, 14.11. 04:50, 15.11. 04:40, 16.11. 04:50 and 12:40–13:40, and 17.11. 04:50–05:00, 09:40. (`sar` times converted from UTC.) At 09:45 `top` showed `ksoftirqd/1` at 100 % with about 60 packets/s on the wire.
- **Only CPU 1 is affected because the NIC has a single queue** (`numrxqueues 1`, `numtxqueues 1`); all network softirq work lands on one core. `/proc/net/softnet_stat` shows about 15 million time squeezes on CPU 1 (about 0.6–0.9 million on the others), and `ksoftirqd/1` has used 512 CPU minutes since boot (89 days).
- **The guest sees the hypervisor stall.** The kernel log has `NETDEV WATCHDOG: transmit queue 0 timed out` (up to 19 s) and `TX timeout` on `virtio_net` at 06:49 on 17.11., soft lockups of 22–269 s on all three CPUs at 06:49–06:56, `rcu_preempt detected stalls`, and stacks in `kvm_flush_tlb_multi` (a vCPU waiting for another that the host did not schedule). The NIC reports `tx_queue_0_tx_timeouts: 5`. This points at host-side contention or a virtio/vhost issue, not at the guest's own load. Steal time itself is only 1–2 %, so the host stalls are short but severe.
- **Not the firewall or conntrack.** UFW logs about 10 000 blocked scan packets over several days (about 1 per few seconds); conntrack held 268 of 262 144 entries. The `UFW BLOCK` log lines are cheap at that rate. `qdisc fq_codel` dropped 97 packets in 90 days. No NIC errors or drops except the 5 TX timeouts.
- **Not memory.** 3.6 GB in use of 7.9 GB, swap barely touched.
- **Traffic is large but steady.** Since boot lc-db sent 3.66 TB and received 95 GB (about 5.4 MB/s average out), almost all of it to lc-main (236 MongoDB connections from 95.216.45.27). MongoDB listens on the public address 95.216.45.31:27017 as well as loopback; UFW blocks outside sources (a scan of port 27017 from 84.248.79.210 was visible and blocked). Binding to the private address only would remove it from scans.
- **I did not see a backup process at 09:30.** The earlier 60 MB dump overloaded the same single-queue path, but the 09:30 stall happened without it as far as `sar` shows (I did not look at what ran on lc-main at that time). The dump is a trigger, not the cause. I could not read root-only logs or `perf`, so which packets keep `ksoftirqd/1` busy at 60 packets/s is not established.

## Suggested follow-ups (need the maintainer)

1. Ask the hosting provider about vCPU scheduling and `virtio_net` TX timeouts on lc-db (kernel stack traces above are the evidence), and ask for a multiqueue virtio NIC (`queues=3`, then `ethtool -L enp6s18 combined 3`), which spreads softirq work across the three cores.
2. Bind MongoDB to the private interface only.
3. Add a Prometheus alert on `softirq` CPU per core and on `NETDEV WATCHDOG` in the kernel log (node-exporter already runs on lc-db).
4. Keep the backup session's work (rate limiting, off-peak timing) in mind: a dump adds load to a path that already stalls without it.
